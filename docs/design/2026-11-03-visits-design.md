# visits（訪問記録）設計

日付: 2026-11-03 / 状態: レビュー済み・承認待ち

## 1. 目的（なぜ作るか）

動物園・水族館・牧場・美術館など「行った場所」の記録を、現在 Notion の表 2 枚と NEXT チェックリストで管理している。これを cabinet に移す。

- 主な使い方は **「今年／去年は何回くらい、どこに行ったか」を振り返ること**。
- cabinet に入れる理由は、撮った写真と訪問記録を結びつけられること（Notion では不可）。コンセプト「世界を知るための、私的な図鑑」の延長として、図鑑（モノ）に対して「行った場所（コト）」を足す位置づけ。
- Notion からは卒業する（併用しない）。

## 2. ゴール / ノンゴール / アンチゴール

**ゴール**

1. 訪問記録（日付・場所・種類）を 1 本の時系列で閲覧でき、種類でフィルタできる。
2. 年ごとにまとまり、各年にサマリー（訪問数・種類別内訳・ユニークな場所数）が出る。
3. 訪問に紐づく写真を見られる（日付で自動紐付け＋同日複数訪問の日は写真ごとに手動選択）。
4. 訪問ごとに短い自由記述メモを書ける（任意）。
5. 「行きたい場所」を日付なしで並べられ、行ったらワンアクションで訪問に変換できる。
6. 訪問の追加・編集・削除を UI から行える（行ったあとに Mac で入力する運用）。
7. Notion の既存データを移行する。

**ノンゴール**

- スマホ・外出先からの入力（Tauri は macOS 専用）。
- 「去年の今ごろ」表示（本人が不要と判断）。
- 星評価などの採点、予定日つきの計画、グラフ描画（月別棒グラフなど）。
- 場所マスタ（住所・地図・営業時間）の管理。

**アンチゴール**

- 既存の gallery（カテゴリ／photos.json／species.json）の構造を歪める。visits をカテゴリとして扱わない。
- mokomoko デザインシステムの逸脱（新色・新フォント・塗りボタン）。

## 3. 決定事項（本人が決めたこと）

| 項目 | 決定 |
|---|---|
| cabinet に混ぜるか | 混ぜる（別アプリにしない） |
| 動物園系と美術館系 | 1 本の時系列に統合し、種類でフィルタ |
| 見た目のベース | 年ごとの縦リスト（モックアップ案 A）。「去年の今ごろ」欄は付けない |
| 年サマリー | 訪問数 + 種類別内訳 + ユニークな場所数（リピート数）。例: `2025 — 28 visits ・ 動物園 12 / 水族館 6 / 美術館 8 / 牧場 2 ・ 24 か所（リピート 4）` |
| 同日に複数訪問の日の写真 | 写真ごとに手動で訪問を選ぶ |
| メモ | 訪問ごとの短い自由記述（例「モネが良かった」）。任意 |
| 計画 | 日付なしの「行きたい場所」リスト（Notion の NEXT 相当） |

## 4. 私（設計者）の判断 — 要確認

以下は会話で本人が決めたものではなく、設計者の案。

- データは `parent_dir` 直下の `visits.json` 1 ファイル。`visits`（配列）と `wishlist`（配列）を持つ。
- 写真への紐付けは `photos.json` の任意フィールド `visit`（訪問 ID）で保存。
- 手動選択 UI は、既存のライトボックスの鉛筆ボタン編集パネルに「訪問」セレクトを足す。候補はその写真の撮影日と同じ日の訪問。
- 種類（kind）は固定リストにせず、データから動的にフィルタボタンを生成する（`tags` と同じ流儀）。
- 年サマリーはフィルタの影響を受けない（常に年全体の内訳を出す）。リスト行だけがフィルタされる。
- ヘッダーに `gallery | visits` のモード切替を置く。

## 5. データモデル

### 5.1 `<parent_dir>/visits.json`

```json
{
  "visits": [
    {
      "id":    "2025-10-12-artizon",   // 必須・一意・不変（photos.json から参照される）
      "date":  "2025-10-12",           // 必須 YYYY-MM-DD
      "place": "アーティゾン美術館",     // 必須
      "event": "葛飾北斎展",            // 任意（特別展など）
      "kind":  "美術館",                // 必須（自由文字列。フィルタ用）
      "note":  "モネが良かった"          // 任意・短い自由記述
    }
  ],
  "wishlist": [
    { "id": "w-ikaho", "place": "伊香保グリーン牧場", "kind": "牧場", "note": "" }
  ]
}
```

- ファイルが無くても gallery は動作する（visits モードは空表示）。
- `parent_dir` 直下の *ファイル* なのでカテゴリ列挙（画像を含むサブフォルダ）には影響しない。
- 「行った」操作: wishlist の項目を削除し、日付（デフォルト今日、編集可）を付けて visits に追加する。

### 5.2 `photos.json` への追加

任意フィールド `visit`（訪問 ID）。

- 写真に `visit` があればそれが常に優先。
- `visit` が無く、写真の `date` に一致する訪問がちょうど 1 件なら、実行時に暗黙で紐付ける（ファイルには書かない）。
- 一致が 2 件以上（同日複数訪問）で `visit` が無い写真は **未割り当て**。訪問詳細に「この日の未割り当て写真」として出し、手動選択を促す。
- 一致が 0 件の写真は紐付けなし。
- 注意: `src-tauri/src/scan.rs` の `MANUAL_FIELDS`（現状 `species` / `title` / `tags`）に `visit` を足さないと、rescan／ウォッチャー再走査で `visit` が消える。必須対応。

## 6. UI

- `gallery | visits` モード切替（ヘッダー）。visits モードでは種類フィルタボタン（データから生成）を表示。
- 年ごと（新しい年が上）にグループ化。年見出しの直下にサマリー 1 行。
- 行: `MM/DD  場所 · イベント  種類  写真枚数`。クリックで詳細（インライン展開またはパネル）。
- 詳細: メモ（編集可）、紐づく写真のサムネ、未割り当て写真（該当日に複数訪問がある場合）、訪問の編集・削除。
- 「行きたい場所」: リストと追加入力、各項目に「行った」アクション。置き場所（画面上部／下部／別セクション）は実装側で決めてよい。
- 訪問の追加フォーム: 日付・場所・イベント・種類・メモ。
- デザインは mokomoko 厳守（IBM Plex Mono、`#0a0a0a` 背景、アクセント `#44aaff` のみ、透明背景＋ボーダーのボタン、角丸 2/3/4px）。

## 7. 技術的制約

- `index.html` にインラインスタイル／`<script>` ブロックを足さない。
- `gallery.js` にグローバル変数を足さない。UI は新ファイル（例 `src/visits.js`）に分けてよいが、同様に IIFE で包み、gallery.js との連携手段は実装側で決める。
- DOM 挿入は `textContent` または `esc()` のみ（XSS 対策）。
- 現状 watcher は **アクティブなカテゴリのフォルダのみ** を監視している（`watcher.rs`）。`visits.json` は `parent_dir` 直下にあるため、外部編集の自動リロードをしたい場合は監視対象の追加が必要（任意。アプリ内編集のみなら不要）。
- 訪問詳細は全カテゴリ（animals / arts / food …）の写真を横断して集める必要がある。現在の `read_photos_json` はアクティブカテゴリ分のみなので、カテゴリ横断で読む手段が要る。
- 純粋ロジック（年サマリー集計、日付による写真↔訪問の紐付け、ユニーク場所数）は、テストを先に書いてから実装する（TDD）。
- 写真・`photos.json`・`visits.json`・移行元データはリポジトリに含めない（個人データ）。`.superpowers/` は `.gitignore` に追加する。
- `CLAUDE.md` に `visits.json` スキーマの節を追加する。

## 8. データ移行（Notion → visits.json）

移行元は本人が貼り付けた 2 表（動物系 36 件、美術系 33 件）と NEXT 4 件。変換は 1 回限りで、生成した `~/Pictures/album/visits.json`（リポジトリ外）に出力する。

変換ルール（設計者の判断）:

- 日付 `2026年10月3日` → `2026-10-03`。
- 美術系の `場所@イベント` は `@` で `place` と `event` に分割（例 `横浜市美術館@佐藤雅彦展` → place `横浜市美術館`, event `佐藤雅彦展`）。
- 動物系の「種類」（牧場／水族館／動物園）はそのまま `kind`。
- 美術系は `kind` を `美術館` とする。ただし名称に「博物館」を含むもの（福岡市博物館、江戸東京博物館、神奈川県立生命の星・地球博物館）は `博物館`。
- 場所が不明確な行（`六本木クロッシング`, `クロード・モネ展`, `ロン・ミュエク展`, `ピクサーの世界展`, `N’s Yard`）は推測で補完せず、書かれた文字列を `place` にそのまま入れる。
- NEXT の kind: 伊香保グリーン牧場＝牧場、埼玉県こども動物自然公園・群馬サファリパーク・市川市動植物園＝動物園。
- `id` は `日付-連番` など一意で不変になる形式。同日複数件（2025-10-12、2026-03-27、2026-04-27）でも衝突しないこと。

### 8.1 移行の進め方（設計者の判断）

- 移行元の 69 行＋NEXT 4 件は本人が会話に貼り付けたもの。リポジトリには置かない。実装時に、変換スクリプトを書き、貼り付けデータを一時ファイル（スクラッチ領域）に置いて 1 回実行し、`~/Pictures/album/visits.json` を生成する。
- 変換ロジックのテストには、典型行（`@` 分割あり／なし、同日複数件、場所不明の行）を数行だけインラインで使う。実データはテストに含めない。

## 9. エッジケースの扱い（設計者の判断）

- **写真の保存先**: 手動で訪問を選んだ結果は、その写真が属するカテゴリの `photos.json` に書く。書き込みコマンドはカテゴリ名を引数に取る（アクティブカテゴリ限定にしない）。
- **カテゴリ横断の写真を開く**: visits 画面で別カテゴリの写真を開くときは、アクティブカテゴリをその写真のカテゴリに切り替えてからライトボックスを開く（species 描画がカテゴリ依存のため）。
- **訪問の削除**: 写真側の `visit` は書き換えない。存在しない ID を指す `visit` は実行時に「紐付けなし」として扱い、日付ベースの暗黙紐付けにフォールバックする。削除時に写真への波及書き込みはしない。
- **訪問の日付変更**: 明示的な `visit` を持つ写真はそのまま紐づいたまま（日付が一致しなくなってもよい）。
- **ユニークな場所数**: `place` の完全一致で数える。正規化はしない。リピート数 = 訪問数 − ユニークな場所数。
